# Envelope step (step C)

Proves that the envelope published with the proof encrypts the document's real DG1 (the MRZ) to the given viewer key:
- the eContent (LDS security object) hashes to step B's `messageDigest`;
- it lists the hash of exactly this DG1;
- the document hasn't expired at the proof date;
- its issuing state is the country of the CSCA leaf from step A;
- the ciphertext is DG1 under a key wrapped to the viewer, bound to `context`;
- the nullifier is the document's in `scope` (0 when `scope` is 0).

DG11 isn't carried. It would add 43k–144k gates to every proof (see *DG11* below and ARCHITECTURE.md, *Future improvements*).

There is one circuit per (eContent hash, data group hash) pair and eContent size bucket, generated by `rust/eid-vectors` under `noir/circuits/envelope/<econtent hash>_<dg hash>/lds_<bucket>`:
- hashes: SHA-1, SHA-256, SHA-384 and SHA-512, all 16 pairs (issuers don't always use the same hash for both);
- buckets: 512, 1024 and 1536 bytes (16 data groups with SHA-512 hashes take about 1.2 kB).

## Interface

```noir
fn main(
    date: u64,                                      // proof date D, unix seconds
    context: Field,                                 // the transfer the envelope is bound to
    scope: Field,                                   // the nullifier's scope; 0 for none
    viewers: [EmbeddedCurvePoint; 1],               // the Grumpkin viewer key, fresh per transfer; (0, 0) is rejected
    w: eid_steps::envelope::Witness<E>,
) -> return_data [Field; 18]                        // eid_steps::envelope::flatten, to kernel_envelope
```

`Witness` holds:
- step B's commitment preimage (salt, country, `messageDigest` zero-padded to 64 bytes, its length);
- the eContent zero-padded to `E`, and the offset of the DG1 entry in it;
- DG1 in a 95-byte buffer;
- the ephemeral scalar `e` and data key `K`.

`Outputs` is:
- `sod_commitment`: must equal step B's output;
- the `Envelope`: `E = e·G`, the wrapped key, and 6 ciphertext fields;
- the `nullifier` in `scope`.

## Statement

With `p = eid_steps::envelope::check(date, w, hash_oid)`, the circuit asserts:

1. **The eContent is an LDS security object** (`eid_der::parse_lds`):
   - version 0, or version 1 with `ldsVersionInfo`;
   - its hash algorithm is the circuit's data group hash (NULL parameters optional);
   - at most 16 `DataGroupHash` entries, each a single-byte data group number 1–16 with a hash of the right length;
   - DG1 listed exactly once, at `dg1_offset` (other data groups are walked but not interpreted);
   - zeros after its DER length.
2. **Step B signed it.** The eContent hash (circuit's eContent hash) equals `messageDigest`, and `digest_len` is that hash's size.
3. **DG1 is the listed one.** DG1's hash equals the hash listed for it.
4. **DG1 is an MRZ** (`parse_dg1`):
   - it is `61 L 5F1F L' MRZ`, with an 88-character (TD3, passport), 72-character (TD2) or 90-character (TD1, ID card) MRZ, followed by zeros;
   - its issuing state, normalised with `csca_registry::country_from_mrz` (`D<<` → `DEU`), equals the committed country.
5. **Not expired.** The MRZ date of expiry, YYMMDD read as 20YY, ends on or after `date`: `date ≤ days(20YY-MM-DD)·86400 + 86399`.
6. **The envelope** is `eid_envelope::seal(viewers, e, K, context, plaintext(DG1))`: see [noir/lib/envelope](../../noir/lib/envelope/README.md). The plaintext holds DG1's length and the whole zero-padded buffer, so viewers get exactly the bytes whose hash was checked.

7. **The nullifier** is `eid_envelope::nullifier(scope, digest, digest_len)`: `H(NULLIFIER, scope, digest_len, pack_be(digest))` over step B's `messageDigest`, or 0 when `scope` is 0 (see *Nullifier*).

The outputs go through the databus to `kernel_envelope`, which checks `sod_commitment` against step B and makes date, context, the viewer key, the envelope, the scope and the nullifier public ([FOLDING.md](../FOLDING.md), [VERIFY.md](../VERIFY.md)).

## Nullifier

A verifier that needs Sybil resistance (one document, one account) picks a scope, for example `H(chain id, contract, purpose)`, and records each nullifier it accepts in that scope. Two proofs of the same document in the same scope carry the same nullifier, whatever their salts and envelope randomness; in different scopes they're unrelated, so proofs stay unlinkable across applications. With `scope = 0` the nullifier is 0 and nothing is linkable, as before.

It's derived from the SOD's `messageDigest` (the hash of the eContent) rather than from anything else on the chip:
- **fixed at issuance:** the SOD is written once, so every proof of the document gets the same value;
- **high entropy:** the eContent lists the hash of DG2 (the face image), so the digest can't be guessed;
- **not derivable by viewers:** they see DG1 only, so they can't compute a document's nullifier from what they decrypt;
- **not malleable:** the SOD signature would be (an ECDSA signature `(r, s)` also verifies as `(r, n − s)`), and so would give one document two nullifiers;
- **not guessable:** MRZ fields (document number, birth date) have little entropy, so a nullifier over them could be recomputed by anyone holding a copy of the passport data.

`digest` is the same `messageDigest` bound to step B's signature through `c_B` and to the eContent by check 2, so the prover can't choose it.

Limits:
- **Per document, not per person.** A renewed passport or a second nationality gives another nullifier.
- **Anyone who read the chip** (an NFC read, not an optical MRZ scan) has the SOD and can compute the nullifier for any scope: they can test whether the document is registered there, or claim the nullifier first.

## DG11

The issuer hashes each data group separately, so DG1 alone is fully bound to the signature and DG11 can simply be left out. Carrying it would mean hashing a fixed 512-byte buffer on every proof, whether or not the document has DG11. Measured on the 512-byte eContent bucket with a SHA-256 eContent hash, that adds 43k gates for SHA-256 data group hashes (+57%), 96k for SHA-1 and 144k for SHA-512. It can be added back as separate envelope variants if viewers need the details it carries.

## Review notes

- **Dates.** The MRZ date is taken as UTC and 20YY; no document valid today expires in the 1900s. MRZ check digits aren't verified: the data group is signed, so they add nothing.
- **The eContent type isn't read from the SOD.** Parsing it as an LDS security object is enough, since that structure is what the issuer signed. DG1's hash is compared as raw bytes at an offset the walk has validated.
- **Duplicate DG1 entries** make the document unprovable rather than ambiguous.
- **One viewer key: the receiver's, fresh per transfer.** The receiver gives the sender a new Grumpkin key off-chain before each transfer; the key is public, so reusing it would link the transfers it appears in. The circuit only rejects `(0, 0)`: freshness isn't enforced in-circuit or by the verifier. The receiver checks the proof's viewer key is the one it issued, then opens the envelope with that key's secret (VERIFY.md, *Receiver*); it keeps the secret of every key it issued. The encryption's own review notes are in [noir/lib/envelope](../../noir/lib/envelope/README.md).
- **Sizes.** An eContent longer than 1536 bytes is unprovable.

## Tests

- **`noir/lib/steps`:** `envelope::check` is run on synthetic documents:
  - LDS v0 (SHA-256) listing DG1, DG2, DG11 and DG14, and v1 (SHA-1 eContent, SHA-512 data groups) without DG11;
  - `parse_dg1` on TD1, TD2 and TD3 specimens (check digits match ICAO 9303).

  The negative cases cover:
  - expiry (the last valid day passes, the next second fails);
  - another country and another hash algorithm;
  - a DG1 offset at another entry;
  - padding after the eContent;
  - a wrong `messageDigest` and a tampered DG1;
  - an MRZ of another length;
  - output binding, including `context`.
- **`noir/lib/envelope`:** an envelope sealed by `rust/eid-envelope` must be reproduced field for field, and is opened by its viewers.
- **Circuits:** each of the 16 hash pairs has a `Prover.toml` from a synthetic document. They alternate LDS v0/v1 and whether DG11 is listed, and CI runs `nargo execute` on all of them.
