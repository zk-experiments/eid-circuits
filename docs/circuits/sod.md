# SOD step (step B)

Proves that the DSC from step A signed the document's security object: the DSC key, read from the same `TBSCertificate` step A verified, signed the SOD's signed attributes, and those attributes carry a `messageDigest`. Step C checks that digest against the LDS security object (eContent). There is one circuit per DSC signing configuration and `TBSCertificate` size bucket, generated by `rust/eid-vectors` (`eid-vectors circuits`) under `noir/circuits/sod/<group>/<variant>/tbs_<bucket>`, with the same groups, variants and buckets as the [DSC step](dsc.md).

## Interface

```noir
fn main(
    dsc_salt: Field,        // step A's salt
    dsc_hash_id: u8,        // step A's hash id
    country: [u8; 3],       // step A's country (ICAO alpha-3)
    salt: Field,            // blinds this step's commitment
    tbs: [u8; T],           // the DSC TBSCertificate, zero-padded (same bytes as step A)
    attrs: [u8; 256],       // SignerInfo signedAttrs in signed form (tag 0x31), zero-padded
    md_offset: u32,         // offset of the messageDigest attribute in attrs
    // RSA:   redc: [u128; N], signature: [u8; K]
    // ECDSA: r: [u8; S], s: [u8; S]
) -> return_data [Field; 2] // [DSC commitment, SOD commitment]: the record noir-zk's kernel reads (c_A the link in, c_B the link out)
```

Only the signed attributes and the DSC signature are taken from the SOD. The rest of the CMS `SignedData` wrapper (certificates, digest algorithm sets, unsigned attributes) doesn't affect the statement.

## Statement

With `(f, a) = eid_steps::sod::parse(tbs, attrs, md_offset)`, the circuit asserts:

1. **The DSC buffer is a TBSCertificate**, as in step A (`eid_der::parse_tbs`, zero padding past `f.len`).
2. **The DSC key has the circuit's type.** It's read from the `subjectPublicKeyInfo` at `f.spki_offset`:
   - **RSA** (`eid_der::spki_rsa`): the algorithm is rsaEncryption or id-RSASSA-PSS. The modulus is a minimal positive INTEGER of at most `K` bytes (the RSA library also asserts its top bit, so it is exactly `8·K` bits). The exponent is at most 4 bytes; the RSA library requires it odd and below 2^17.
   - **ECDSA** (`eid_der::spki_ec`): the algorithm is id-ecPublicKey. The parameters are the circuit curve's named OID, or explicit `ECParameters` (which ICAO 9303 asks for) whose prime `p` and coefficients `a`, `b` equal the circuit curve's (`eid_der::curves`). The point is uncompressed, `0x04 ‖ x ‖ y`, with full-size coordinates. The ECDSA library checks that it's on the curve.
3. **The signed attributes are well formed.** `attrs` is a DER SET of at most 8 attributes that exactly fill it, followed only by zeros. `md_offset` is the start of one of them, and that attribute is `SEQUENCE { id-messageDigest, SET { OCTET STRING d } }` with exactly one value of 20, 28, 32, 48 or 64 bytes.
4. **The DSC signed them.** The signature over `hash(attrs[..a.len])` verifies under the DSC key with the circuit's scheme (`eid_rsa` or `eid_ecdsa`).
5. **Outputs.**
   - `dsc::commitment(dsc_salt, country, dsc_hash_id, tbs, f.len)`: the pipeline kernel checks it equals step A's output (the link), which ties this `TBSCertificate`, and so the DSC key, to a registered, unrevoked CSCA.
   - `sod::commitment(salt, country, a) = H(salt, country, digest_len, pack_be(digest))`, with the digest zero-padded to 64 bytes: passed to step C.

## Review notes

- **The attribute tag.** In the SOD the signed attributes are `[0] IMPLICIT` (`0xA0`), but RFC 5652 §5.4 signs their SET encoding (`0x31`). The prover supplies the SET form, and the circuit rejects `0xA0`.
- **Only messageDigest is interpreted.** contentType and signingTime aren't checked. The eContent type is enforced by step C, which parses the eContent as an LDS security object. The DSC's own validity dates aren't checked either: documents stay valid after their DSC's private key usage period ends, as in ICAO 9303.
- **The digest algorithm isn't read from the SOD.** Step C hashes the eContent with the algorithm of its own variant and must match `digest_len` and the digest bytes, so an algorithm mismatch fails there.
- **Explicit parameters are bound by `p`, `a` and `b`.** The generator, order and cofactor aren't compared. A key is only usable if its point is on the circuit's curve, and the signature is checked with the standard generator and order, so different values there can only make an honest signature fail, not make a false one pass. Coefficients are compared as numbers: issuers write them with the SEC 1 width, one extra leading `0x00`, or leading zeros dropped.
- **Configurations.** The 31 configurations mirror the CSCA signing configurations of the DSC step. Real DSC key and scheme statistics per country (ICAO PKD DSC list) would refine the set.
- **Costs** per circuit are in `docs/data/circuit-sizes.json`. All SOD circuits are below the 2 GiB memory cap.

## Tests

- **`noir/lib/steps`:** `sod::parse` and the DSC key read are checked on five synthetic documents: rsaEncryption and id-RSASSA-PSS keys, the named P-256 curve, and explicit brainpoolP256r1 and P-521 parameters. The negative cases cover:
  - `md_offset` inside an attribute, or at a non-messageDigest attribute;
  - non-zero padding after the attributes or the certificate;
  - attributes in their `[0]` form;
  - an RSA key read as EC, and an EC key read as RSA;
  - a named curve or explicit parameters of another curve;
  - a modulus larger than the circuit's;
  - commitment sensitivity to every input.
- **`noir/lib/der`:** the key read is also checked on the 33 real certificates, 12 of them with explicit EC parameters (one with 49-byte, `0x00`-prefixed coefficients).
- **Circuits:** every configuration has a `Prover.toml` built from a synthetic document signed with a deterministic key (`rust/eid-vectors/src/mock.rs`). Each signature is first verified with csca-registry's RustCrypto verifier. CI runs `nargo execute` on all 31.
