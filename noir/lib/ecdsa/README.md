# eid_ecdsa

ECDSA signature verification (SEC 1 §4.1.4, FIPS 186-5 §6.4.2) as used by CSCAs and DSCs. It covers P-256, P-384, P-521 and brainpoolP256r1, brainpoolP384r1 and brainpoolP512r1. Curve arithmetic comes from `noir-lang/noir_bigcurve` v0.14.0, vendored; field arithmetic from `noir-lang/noir-bignum` v0.10.0.

## API

| function | key and scalar sizes |
|---|---|
| `verify_p256::<D>(x, y, r, s, digest)` | 32 / 32 bytes |
| `verify_p384::<D>(…)` | 48 / 48 |
| `verify_p521::<D>(…)` | 66 / 66, `D ≤ 65` |
| `verify_bp256::<D>(…)` | 32 / 32 |
| `verify_bp384::<D>(…)` | 48 / 48 |
| `verify_bp512::<D>(…)` | 64 / 64 |

- `x` and `y` are the public key's affine coordinates, big-endian (the SEC1 uncompressed point without the `04` prefix).
- `r` and `s` are the signature scalars, big-endian and left-padded. The DER `SEQUENCE { r, s }` is decoded by the prover. The signature value isn't itself signed, so the circuit only needs `(r, s)`, not the DER bytes.
- `digest` is the message digest for any hash.

## Construction

`verify_core::<C, Fq, Fr, S>` is shared by all curves:
1. It asserts `qx` and `qy` are canonical (`< p`, via `validate_in_field`), and that `Q = (qx, qy)` is a finite point on the curve (`validate_on_curve`).
2. It asserts `r` and `s` are in `[1, n − 1]`: `validate_in_field` proves `≤ n`, and `assert_is_not_zero` rules out `0` and `n`.
3. It computes `u₁ = e / s` and `u₂ = r / s` with constrained division in the prime scalar field.
4. It computes `R = u₁·G + u₂·Q` as one multi-scalar multiplication (`evaluate_linear_expression`) and asserts `R ≠ ∞`.
5. It returns `R.x`, canonical.

Each wrapper then:
- turns the digest into `e` with `digest_to_scalar_bytes`. That's `bits2int` for these curves: the leftmost `⌈bits(n)/8⌉` bytes when the digest is longer, right-aligned when it is shorter. For P-521, `8·D ≤ 520 < 521`, so the digest is used whole.
- asserts `R.x ≡ r (mod n)`, comparing `R.x` read as a scalar-field element with `r`. For every supported curve `p < 2^bits(n)`, so `R.x` fits.

## Curves

P-256 and P-384 are noir_bigcurve's own. P-521 and the brainpool curves are generated by `rust/eid-vectors` (`eid-vectors curves`) into `noir/vendor/noir_bigcurve/src/curves/eid_*.nr`:

- **Domain parameters** are copied from csca-registry's curve table, which was generated with OpenSSL. They're re-checked at generation time: the generator is on the curve, `n·G = ∞`, and `p ≡ 3 (mod 4)`.
- **Field parameters:**
  - modulus limbs: 120-bit, little-endian;
  - `double_modulus`: computed by noir-bignum's `get_double_modulus` rule;
  - `redc`: `floor(2^(2·bits + 6) / m)`.
- **Scalar slices** follow `ScalarField::from_bignum`'s count, `(bits mod 120)/4 + 1 + 30·(limbs − 1)`: 65, 97, 129 and 131 for 256, 384, 512 and 521 bits.
- **Offset generator.** For counter = 0, 1, …, the generator takes `x = SHA-256("eid-circuits offset generator" ‖ curve name ‖ counter) mod p` until `x³ + ax + b` is a square, and uses the even root as `y`. The final offset generator is `2^(4·(S − 1))` times that point.

  noir_bigcurve's own `hash_to_curve` isn't used, because its seed packing never writes the seed into the hashed array. An offset generator only needs an unknown discrete logarithm, which a hash-derived point provides.

## Soundness notes

- **Key binding is the caller's job.** The circuit must source `x` and `y` from a registry leaf (a CSCA key) or from the signed DSC `SubjectPublicKeyInfo` (a DSC key).
- **Incomplete formulas.** noir_bigcurve's affine addition rejects equal or opposite points. Offset generators keep a scalar multiplication away from those cases. A proof can't be made to accept a wrong result through them; the worst case is that proving fails, and there are no known failures for real keys.
- **Scalars.** `e` may be `≥ n`; scalar-field arithmetic works modulo `n`. `u₁` and `u₂` are range-checked when they're decomposed into windowed slices (`ScalarField::from_bignum` calls `validate_in_field`).
- **Low-S isn't required.** Issuers don't normalise `s`, and ECDSA verification accepts both `s` and `n − s`. This only matters to a caller that treats `(r, s)` as a unique identifier.

## Tests

- **`src/vectors.nr`** is generated from 14 real CSCA certificates in the DE and IT master lists, re-verified with RustCrypto before emission. It covers all six curves with SHA-1, SHA-256, SHA-384 and SHA-512, including keys with explicit domain parameters (for example LT on brainpoolP256r1). CI fails if the file is stale.
- **`src/tests.nr`:**
  - the generator and both offset generators of every generated curve are on the curve;
  - tampered `r`, tampered `s`, another message, another key (`−Q`);
  - a key off the curve, `r = 0`, `s = n`;
  - an oversized P-521 digest;
  - digest truncation and padding.
- **Group order and the final offset generator** are re-checked with independent big-integer arithmetic by `cargo test` in `rust/eid-vectors`. Doing it in-circuit would need incomplete additions of a point with itself.
